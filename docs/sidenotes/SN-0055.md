# Timeout vs cancel UX (not for now)

**Disposition:** not used. No current product scenario that requires distinct user messaging for HTTP timeout vs cancellation. Ignore for modularization.

**What it would be:** different user-facing strings (and maybe badge states) when a request times out versus when the user or navigation cancels work.

**Why parked:** the product does not currently need that distinction as a planned UX. Result/`Match` error strings can stay simple. Not a RiverBooks or architecture item.

**Production impact:** none (string/UX only).

**Revisit when:** a real UX requirement appears (e.g. long-running fetch with explicit cancel control). Not scheduled.
