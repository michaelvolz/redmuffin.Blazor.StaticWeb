We need to analyze all patterns and decisions made during the CRAP cleanup
session and document them thoroughly so any LLM writing or changing our
code from the beginning applies these techniques. The quality tools should
not find anything because the code is written correctly from the start.

Capture the specific refactoring patterns we discovered:

1. Giant switch expressions (CC>15) → split into category-level dispatcher
   methods
2. CLI option boilerplate → extract to static readonly fields; Create()
   becomes pure assembly with CC=1
3. Validation/orchestration logic → extract into public static helpers so
   wrappers have CC=2 (passes at any coverage)
4. `or` pattern merging to reduce switch arm count
5. Long methods → extract named sections into helpers (reveals structure)
6. The three-category taxonomy: untested, structural, boilerplate
7. CC=8 methods need >87.5% coverage; CC=7 methods need >84%; CC=2 passes
   at 0%
8. Making Execute() methods public static so integration tests provide
   coverage

Rules like "no `#pragma warning disable` — every warning is a signal to
improve code" and "Zero-warnings policy as quality mechanism, not
compliance checkbox" must also be codified.

The target: zero quality gate violations should be achievable from the
first write, not something we hunt down after the fact.
