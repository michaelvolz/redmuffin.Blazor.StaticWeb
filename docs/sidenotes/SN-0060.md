# Move `.razor` into module projects (under discussion — need deploy size facts)

**Disposition:** **not decided.** Preference is to **move** pages/components into module assemblies for stronger RiverBooks colocation, **if** published deploy size does not grow more than about **5%**. Without measured data, do not land the move.

**What it is:** ship Blazor UI (`.razor` / page code-behind) from `{Module}` (or a UI project per module) instead of only from the host `Features/` project. Host would stay composition root and maybe shell layout only.

**Why it is attractive:** feature UI lives with Contracts/handlers; clearer ownership; matches “module owns the capability” more completely than host-only pages.

**Why it needs facts first:** extra assemblies, static assets, and linker graph can increase **WASM/SWA publish output**. Preference threshold: if total published size (or primary download metric we already track) grows **over ~5%**, stop and re-evaluate; if under ~5%, prefer the move.

**Required measurement before decide (task when tackled):**

1. Baseline: current `dotnet publish` (or existing SWA/WASM size report) for the production-like configuration — record total output and key `_framework` / compressed sizes.
2. Spike: one module with one page moved (e.g. ApiHealth only) behind a throwaway branch or worktree.
3. Re-publish with the same configuration; diff absolute and **percent** size.
4. Note any extra downloads (lazy assemblies) vs one-shot payload.
5. Document numbers in the conversion artifact; only then ADR or roadmap update.

**Production impact:** possible size and load-path change; not free. Decision is **data-gated**, not taste-only.

**Related standing docs:** roadmap currently keeps pages in host until an ADR revises UI ownership — this sidenote is the explicit “we want to revisit with measurements” ticket.
