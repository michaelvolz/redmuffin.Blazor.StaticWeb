# Fix: Correct WASM Metrics Collection in page-load-timing.js

## Overview

The page-load-timing widget on the production site shows "WASM↓: 5 ms / 0 B" — the WASM download size reads as zero. The WASM files themselves load fine (confirmed via network tab: two `.wasm` files return 200 with real payloads). The bug is in the JavaScript metrics collection code: `findWasmEntry()` searches for `dotnet.native.*.js` (the JS loader, which is often served from cache with `transferSize: 0`) instead of the actual `.wasm` files, and `getAssemblyInfo()` counts framework JS/boot files instead of the real `.wasm` assemblies.

## Problem Frame

The `page-load-timing.js` script was written with an incorrect assumption about .NET 9's WASM loading model. It assumes the `dotnet.native.*.js` file _is_ the WASM resource, but in reality:

- `dotnet.native.<hash>.js` is a JavaScript loader (small, often cached → `transferSize: 0`)
- `redmuffin.Blazor.StaticWeb.<hash>.wasm` is the actual compiled assembly (102 KB, always fetched)
- `redmuffin.Blazor.StaticWeb.Common.<hash>.wasm` is a shared assembly (20 KB, always fetched)

The widget's "WASM↓" line shows the download time/size of the JS loader, not the WASM files. The "Assemblies" count includes `dotnet.js`, `dotnet.runtime.*.js`, `dotnet.native.*.js`, and `blazor.boot.json` — none of which are assemblies.

## Requirements Trace

- R1. `findWasmEntry()` must return the primary `.wasm` resource entry (the app's main WASM file) so that `wasmDownloadSize` reflects actual WASM download bytes.
- R2. `getAssemblyInfo()` must count only `.wasm` files under `_framework/`, not JS or JSON files.
- R3. The fix must not break any existing metric collection (timing marks, memory, LCP, etc.).
- R4. The minified output (`page-load-timing.min.js`) must be regenerated via the project's build pipeline (`compilerconfig.json`).

## Scope Boundaries

- **In scope**: `findWasmEntry()` and `getAssemblyInfo()` in `page-load-timing.js`, plus minified output regeneration.
- **Out of scope**: No changes to the C# `PerformanceMetricsService`, `PageLoadSpeed.razor`, or any other consumer — they call `window.getWasmMetrics()` which already returns the correct shape. No changes to timing mark logic (`markStart`, `markBlazorStart`, `markEnd`).

### Key Technical Decisions

- **Decision**: `findWasmEntry()` should find the main app WASM file (the largest `.wasm` under `_framework/`), not the JS loader.
  - **Rationale**: The widget's "WASM↓" label semantically means "WASM download." The main app WASM file is the most meaningful single-file proxy. If multiple `.wasm` files exist, picking the largest one gives the best single-number signal.
- **Decision**: `getAssemblyInfo()` should count all `.wasm` files under `_framework/` and sum their `transferSize`.
  - **Rationale**: These are the actual compiled .NET assemblies. The previous code counted JS loader files as a "proxy" which was never accurate.

## Implementation Units

- [ ] **Unit 1: Fix `findWasmEntry()` to locate actual `.wasm` files**

**Goal:** Return the primary WASM resource entry (largest `.wasm` file under `_framework/`) instead of the `dotnet.native.*.js` loader.

**Requirements:** R1, R3

**Dependencies:** None

**Files:**

- Modify: `src/redmuffin.Blazor.StaticWeb/wwwroot/js/page-load-timing.js`

**Approach:**

- Change `findWasmEntry()` to filter `performance.getEntriesByType('resource')` for entries whose `name` ends with `.wasm` and includes `_framework`.
- Among matching entries, return the one with the largest `transferSize` (the main app assembly). If no `.wasm` entries exist, fall back to the current `dotnet.native.*.js` behavior as a safety net.

**Patterns to follow:**

- Existing `try/catch` wrapper pattern in the file
- Existing `resources.find()` / `resources.filter()` style

**Test scenarios:**

- Happy path: When `.wasm` files are present in resource timing, `findWasmEntry()` returns the largest one (the main app WASM).
- Edge case: When no `.wasm` files exist in resource timing (e.g., pre-WASM browser), the function returns `null` gracefully.
- Edge case: When multiple `.wasm` files exist (app + shared library), the largest one is returned.

**Verification:**

- `findWasmEntry()` returns a `PerformanceResourceTiming` entry for a `.wasm` file on the live site.
- `wasmDownloadSize` in the widget shows a non-zero byte value matching the actual WASM file size.

- [ ] **Unit 2: Fix `getAssemblyInfo()` to count only `.wasm` files**

**Goal:** Count and sum `transferSize` for actual `.wasm` assembly files, not JS/boot files.

**Requirements:** R2, R3

**Dependencies:** Unit 1 (same file, independent logic but batched together)

**Files:**

- Modify: `src/redmuffin.Blazor.StaticWeb/wwwroot/js/page-load-timing.js`

**Approach:**

- Change the filter inside `getAssemblyInfo()` to only count resources whose name ends with `.wasm` and includes `_framework`.
- Remove the old filter that matched `dotnet.js`, `dotnet.runtime*`, `dotnet.native*`, and `blazor.boot.json`.

**Patterns to follow:**

- Existing `try/catch` wrapper and `resources.forEach()` pattern

**Test scenarios:**

- Happy path: When two `.wasm` files exist (`redmuffin.Blazor.StaticWeb.*.wasm` and `redmuffin.Blazor.StaticWeb.Common.*.wasm`), `assemblyCount` is 2 and `assemblyTotalSize` is the sum of their `transferSize` values.
- Edge case: When no `.wasm` files exist, returns `{ count: 0, totalSize: 0 }`.
- Error path: When `performance.getEntriesByType` is unavailable, returns `{ count: 0, totalSize: 0 }` via the catch block.

**Verification:**

- `assemblyCount` in the widget matches the actual number of `.wasm` files loaded.
- `assemblyTotalSize` reflects the combined transfer size of all `.wasm` files.
