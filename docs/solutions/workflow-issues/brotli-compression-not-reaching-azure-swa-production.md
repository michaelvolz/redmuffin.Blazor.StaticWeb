## Problem

`dotnet publish` generated Brotli-compressed (`.br`) and Gzip-compressed (`.gz`) versions of all static assets during the build phase, reducing file sizes by 60-70%. However, these pre-compressed files were not reaching production. Browsers received uncompressed assets, negating the build-time compression investment and causing larger initial payloads.

## Root Cause

The deployment workflow originally used the SWA CLI (`swa deploy`), which triggered Oryx (Azure Static Web Apps' build engine) to detect and rebuild the application during deployment. Oryx's rebuild overwrote the pre-compressed assets generated by `dotnet publish`, replacing them with uncompressed files.

## Solution

**Replace SWA CLI deployment with `Azure/static-web-apps-deploy@v1` GitHub Action using `skip_app_build: true`:**

```yaml
- name: Deploy to Azure Static Web Apps
  uses: Azure/static-web-apps-deploy@v1
  with:
    azure_static_web_apps_api_token: ${{ secrets.AZURE_STATIC_WEB_APPS_API_TOKEN }}
    repo_token: ${{ secrets.GITHUB_TOKEN }}
    action: "upload"
    app_location: "src/redmuffin.Blazor.StaticWeb/bin/Release/publish/wwwroot"
    api_location: "src/redmuffin.Blazor.StaticWeb.Api/bin/Release/publish"
    output_location: ""
    skip_app_build: true
```

**Key configuration changes:**

| Parameter         | Old Value          | New Value                                | Reason                    |
| ----------------- | ------------------ | ---------------------------------------- | ------------------------- |
| Deployment tool   | `swa deploy` CLI   | `Azure/static-web-apps-deploy@v1` Action | `skip_app_build` honored  |
| `skip_app_build`  | Not set            | `true`                                   | Prevents Oryx rebuild     |
| `output_location` | `"wwwroot"`        | `""` (empty)                             | Signals pre-built app     |
| `app_location`    | Project source dir | Publish output dir                       | Points to built artifacts |

**Verification steps added to workflow:**

1. Post-build check — `find` for `*.br` files in publish output before deployment
2. Post-deployment health check — `curl` with `Accept-Encoding: br` header to verify `content-encoding: br` in response

**Current state (2026-05):** The `Azure/static-web-apps-deploy@v1` GitHub Action with `skip_app_build: true` is the primary deployment path and correctly preserves pre-compressed assets. The `swa deploy` CLI is still used for on-demand deployments from local — it still triggers Oryx rebuilds and should only be used when a full rebuild is desired. Production CI uses the GitHub Action exclusively.

## Prevention

- When using `dotnet publish` for Blazor WASM (which generates pre-compressed assets), always deploy with `skip_app_build: true` to prevent Oryx from rebuilding and overwriting them.
- Add a verification step in the workflow that checks for `.br` file presence in the publish output before deployment.
- The `Azure/static-web-apps-deploy` GitHub Action with `skip_app_build: true` is the Microsoft-recommended pattern when you want full control over the build process.
